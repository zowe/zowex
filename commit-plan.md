### Issue: BPAM write can hang indefinitely when the target data set is password-protected

**Title:** `zowex hangs (WTOR) writing to a legacy password-protected data set via BPAM`

**Body** (copy/paste as-is):

```markdown
## Summary

`open_output_bpam` in `native/c/zam.c` opens the output DCB without first checking
whether the target data set has legacy MVS password protection. On z/OS, OPEN on a
password-protected data set issues a WTOR (write-to-operator-with-reply) to the
system console and blocks until an operator answers it. `zowex server` is a
long-lived RPC process with no console attached, so any request that reaches this
code path would hang forever instead of returning an error — the client sees a
timeout with no diagnostic, and the server thread is stuck until someone replies
to a WTOR on a console that likely isn't being watched.

## Where

- `native/c/zam.c`, `open_output_bpam` (reads the JFCB via `read_output_jfcb`,
  then calls `validate_jfcb_attributes`, which currently checks `jfcbind1` for
  PDS-ness but never inspects `jfcbind2`).
- The password-protection bits are already vendored in `native/c/chdsect/jfcb.h`:
  ```c
  #define jfcbrwpw 0x30 /* PASSWORD IS REQUIRED TO WRITE BUT NOT TO READ */
  #define jfcsecur 0x10 /* PASSWORD IS REQUIRED TO READ OR TO WRITE      */
  ```
- Any BPAM write path is affected — this isn't specific to one command. The
  easiest trigger is the existing `zowex data-set write` command against a
  PDS/PDS-E member (`native/c/commands/ds.cpp`, `handle_data_set_write`), which
  goes through the exact same `open_output_bpam` call.

## Steps to reproduce

This requires a system where **legacy MVS password protection is actually active**
(a `SYS1.PASSWORD` — or site-equivalent — password data set exists and is in
effect). I could not reproduce this end-to-end myself: the LPAR I have access to
(`lpar.1`) has no `SYS1.PASSWORD` data set, so legacy password protection is
inactive there and OPEN never takes the WTOR path regardless of JFCB content.
Treat steps 1–2 as "how this class of protection is normally set up" rather than
a verified recipe for this specific site — confirm against your own system's
security admin / the applicable IBM data set services reference before relying
on it, and record on the issue once someone with access has actually reproduced
the hang.

1. On a system with legacy password protection active, protect a test PDS
   against write access, e.g. via the TSO `PROTECT` command:
   ```
   PROTECT 'YOUR.TEST.PDS' PASSWORD(somepw) GENERATE
   ```
   (exact syntax/options vary by site convention — check what your system
   actually uses to set the "PASSWORD REQUIRED TO WRITE" / "PASSWORD REQUIRED TO
   READ OR WRITE" JFCB indicators before assuming this command is exactly right.)
2. Confirm protection is active, e.g. by attempting a write from an unrelated
   already-password-aware utility and observing the password prompt/failure.
3. Run, against `zowex` (server or CLI, pointed at a build **without** the fix
   in this branch):
   ```
   zowex data-set write "YOUR.TEST.PDS(MEMBER1)" < ./some-local-file
   ```
4. Observe: the command does not return. On the LPAR console (or syslog), a WTOR
   should appear asking for the data set password, with the requesting task/job
   waiting on the reply.

## Expected behavior

`zowex` returns a clean error immediately (no OPEN, no WTOR) explaining that the
target data set is password-protected and unsupported over this RPC path.

## Actual behavior

The write hangs indefinitely (per documented z/OS OPEN behavior for
password-protected data sets — not independently confirmed against this repo's
code by a live run, since no accessible test system currently has password
protection enabled; see "Steps to reproduce" above).

## Suggested fix

Pre-OPEN guard in `validate_jfcb_attributes` (`native/c/zam.c`), right next to the
existing `jfcbind1` PDS check: if `jfcb.jfcbind2 & (jfcsecur | jfcbrwpw)` is set,
fail fast with a clear error instead of proceeding to OPEN. A fix along these
lines is ready — happy to open the PR once this issue exists, referencing it with
`Fixes #<this-issue>`.

## Note on scope

There's a symmetric read-side gap (`zds_read`'s `fopen` path has no equivalent
check, and the read-side indicator lives in the DSCB's `DS1DSIND` byte rather than
the JFCB), but the exact `DS1DSIND` password bit mask isn't yet confirmed against
the DFSMS DSCB reference, so no read-side fix is included here. Filing that as a
separate, follow-up issue once the bit mask is confirmed is probably the right
call rather than guessing at it.
```

Nothing else in this branch rises to "open an issue" — the rest is new capability
in support of `--dsn`, not a pre-existing defect.
